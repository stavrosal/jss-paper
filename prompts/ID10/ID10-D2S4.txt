1. Cyclomatic Complexity (CC) – Κυκλωματική Πολυπλοκότητα
Τι μετράει: Πλήθος των ανεξάρτητων μονοπατιών εκτέλεσης στον κώδικα.

Πρόβλημα: Η ύπαρξη if/else για τους τύπους αποθηκών (π.χ., local vs central) και για τα είδη ΦΠΑ αυξάνει σημαντικά την πολυπλοκότητα.

Αποτέλεσμα: Δυσκολία στη δοκιμή, αυξημένος αριθμός test cases και μεγαλύτερη πιθανότητα λαθών.

2. Cohesion (Συνοχή)
Τι μετράει: Πόσο σχετικές είναι οι λειτουργίες και τα δεδομένα μιας κλάσης μεταξύ τους.

Πρόβλημα: Η κλάση Warehouse κάνει πολλές διαφορετικές δουλειές (κρατά δεδομένα, διαχειρίζεται παραγγελίες, υπολογίζει ΦΠΑ).

Αποτέλεσμα: Χαμηλή συνοχή → δύσκολη κατανόηση και συντήρηση.

3. Coupling (Σύζευξη)
Τι μετράει: Πόσο εξαρτάται μια κλάση από άλλες.

Πρόβλημα: Η αποθήκη πιθανώς εξαρτάται έντονα από τις λεπτομέρειες της κλάσης Item και τις συμβολοσειρές για τύπους.

Αποτέλεσμα: Υψηλή σύζευξη → μικρή επαναχρησιμοποίηση, αυξημένη πιθανότητα ripple effect σε αλλαγές.

4. Lines of Code (LOC) – Γραμμές Κώδικα
Τι μετράει: Το μέγεθος του κώδικα.

Πρόβλημα: Η συνύπαρξη πολλών if/else, επαναλαμβανόμενου κώδικα (duplication) και manual ελέγχων οδηγεί σε αύξηση LOC.

Αποτέλεσμα: Μεγαλύτερος χρόνος ανάγνωσης και εντοπισμού σφαλμάτων.

5. Lack of Cohesion in Methods (LCOM)
Τι μετράει: Πόσο διαφορετικά είναι τα πεδία που χρησιμοποιούνται από κάθε μέθοδο.

Πρόβλημα: Οι μέθοδοι addOrder και calcCost πιθανόν δεν χρησιμοποιούν όλα τα πεδία της κλάσης.

Αποτέλεσμα: Υψηλό LCOM → ένδειξη ότι η κλάση πρέπει να διασπαστεί σε μικρότερες.

6. Maintainability Index
Τι μετράει: Πόσο εύκολα μπορεί να διατηρηθεί ο κώδικας.

Πρόβλημα: Ο μεγάλος, μη δομημένος κώδικας με πολλές ευθύνες και αυξημένη πολυπλοκότητα μειώνει αυτήν τη μετρική.

Αποτέλεσμα: Αυξημένο κόστος συντήρησης και ανάπτυξης.

✅ Σχεδιαστικές Αρχές (Design Principles)
1. Single Responsibility Principle (SRP)
Μια κλάση πρέπει να έχει έναν και μόνο έναν λόγο αλλαγής.

🔧 Εφαρμογή:
Η κλάση Warehouse θα πρέπει να διαχωριστεί σε:

Κλάση για δεδομένα αποθήκης,

Κλάση για παραγγελίες,

Κλάση για πολιτική ΦΠΑ.

2. Open/Closed Principle (OCP)
Οι οντότητες λογισμικού πρέπει να είναι ανοικτές για επέκταση αλλά κλειστές για τροποποίηση.

🔧 Εφαρμογή:
Αντί για if/else σε warehouseType, χρησιμοποιούμε πολυμορφισμό:

Υποκλάσεις LocalWarehouse, CentralWarehouse

Κάθε υποκλάση έχει διαφορετική υλοποίηση για τον υπολογισμό κόστους με ΦΠΑ.

3. Liskov Substitution Principle (LSP)
Οι υποκλάσεις πρέπει να μπορούν να χρησιμοποιηθούν στη θέση των υπερκλάσεων χωρίς να προκαλούν σφάλματα.

🔧 Εφαρμογή:
Κάθε υποκλάση αποθήκης να μπορεί να χρησιμοποιηθεί εναλλακτικά, χωρίς να επηρεάζεται ο κώδικας πελάτης.

4. Dependency Inversion Principle (DIP)
Ο κώδικας υψηλού επιπέδου δεν πρέπει να εξαρτάται από υλοποιήσεις αλλά από αφαιρέσεις (interfaces/abstract classes).

🔧 Εφαρμογή:
Η κλάση Warehouse να εξαρτάται από interface VatPolicy αντί για συγκεκριμένο vatType.
