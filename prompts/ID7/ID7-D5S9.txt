We aim to develop a system for modeling Wedding events. Each wedding will take place in a venue (String) and will have a List of people (assume People class is already implemented). Each wedding event has food catered to the attendants, where the total cost is calculated by the catering company.
Specifically, each person is entitled to one meal, which costs 3€ if its basic, and 3.5€ if its vegan. If there are more than 500 attendants then the prices are -1 / person (that means 2€/basic and 2.5€/vegans).

The wedding also has a photographer that is paid based on the attendants. The base price is 1€/person but if there are more than 600 attendants then the price drops to 0.75€/person.
class Wedding{
	String venue;
	
	List<Person> people;
	
	public void addPerson(Person p){
		this.people.add(p);
	}
	
	public double calculateFoodCost(){
		int vegans = 0; 
		for (Person p : people){
			if (p.isVegan()){
				vegans += 1;
			}
		}
		
		int non_vegans = people.size() - vegans;
		
		double total; // total cost
		if (people.size() <= 500){
			total = non_vegans * 3 + vegans * 3.5;
		}
		else{
			total = non_vegans * 2 + vegans * 2.5;
		}
		
		return total;	
	}
	
	public double calcPhotosCost(){
		double cost;
		if (people.size() <= 600){
			cost = people.size() * 1;
		}
		else{
			cost = people.size * 0.75;
		}
		
		return cost;
	}
		 

}

Yes, there are several code smells in this implementation of the Wedding class that can lead to maintenance issues or design problems. Here's a breakdown of the most notable ones:

1. Data Clumping
Symptom: The costs for food are calculated based on hardcoded values (3€, 3.5€, 2€, 2.5€, etc.), and these values are repeated in the method.

Why it's a problem: If any of these values change, you must update multiple places manually, increasing the chance of introducing inconsistencies.

Refactor Suggestion: Extract these costs into constants or configuration parameters.

2. Magic Numbers
Symptom: Numbers like 500, 600, 3, 3.5, 2, 2.5, 1, and 0.75 appear without explanation.

Why it's a problem: It's unclear what these values represent without reading the logic deeply. This reduces readability.

Refactor Suggestion: Define named constants (e.g., MAX_FULL_PRICE_ATTENDEES, BASIC_MEAL_COST, etc.).

3. Method Responsibility Overlap
Symptom: calculateFoodCost() handles both determining the number of vegan attendees and computing cost.

Why it's a problem: Mixing business logic with data gathering makes the method harder to test and reuse.

Refactor Suggestion: Extract logic to countVegans() or split responsibilities.

4. Primitive Obsession
Symptom: Use of raw double and int for representing monetary values and people categories.

Why it's a problem: Leads to potential errors in logic or representation. Monetary values may require more precision.

Refactor Suggestion: Consider using a Money type or at least BigDecimal in Java for currency.

5. Lack of Encapsulation for Business Rules
Symptom: Business rules (e.g., cost thresholds) are hardcoded inside the Wedding class.

Why it's a problem: Makes changes hard if business rules evolve.

Refactor Suggestion: Encapsulate in strategy classes or a configuration service.

6. Potential Null Pointer Exception
Symptom: The people list isn't initialized in the constructor.

Why it's a problem: addPerson() and the cost methods assume it's not null.

7. Typo or Bug in calcPhotosCost()

8. No Separation of Concerns
Symptom: All logic related to people, food, and photography is inside the Wedding class.
